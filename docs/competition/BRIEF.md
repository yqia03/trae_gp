# 就地取材 · 产品规格

版本：2026-09-12 赛前交付基线。用户要求准备资产与指令，业务实现交给 TRAE。本文件给出可直接实施的默认方案，现场补充要求或用户新指令优先。

## 产品与范围

**把家里已有的，变成今天用得上的。**

「就地取材」面向独居、合租年轻人，把现有食材与闲置物品转成可执行方案。共享流程：拍图或手动录入 → 确认有什么、多少 → 说明限制 → 获得方案、用量与步骤。

- **今晚吃什么（主场景）**：已确认食材 → 一餐菜单、做法、制作顺序。
- **物品第二人生（次场景）**：已确认旧物 → 两种二选一的用途与制作步骤。
- **巧用替代（共享亮点）**：缺料时改用已有资源或调整做法，显示差异，重新规划并核算用量。不是第三个独立应用。

用户已确认：生活创意赛道、合并食材与旧物主题、单机开发、Codex 仅做准备、TRAE 写代码、Google Gemini、指定 Refero 参考。

本包采用的规划默认值：产品名「就地取材」、年轻合租人群、食材优先、旧物次之、默认 2 人与目标 30 分钟、最多补充 2 类消耗品、下述技术栈。它们不是用户逐项明确指定，也不是比赛规则；用户可后续修订，无需在开工时重新选题。

## 三项评分如何呈现

| 评分 | 演示中展示的具体事实 |
|---|---|
| 创新性 | 同一套资源清单做晚餐、改旧物；缺料后按现有资源重新规划，方案内不能重复占用材料。 |
| 应用价值 | 用户得到一餐菜单或一个可动手的旧物用途，具备材料、步骤和必要条件。 |
| 完成度 | 输入、识别纠错、确认、生成、执行连贯；失败可恢复，样例与真实结果明确区分。 |

不声称全球首创，不编造节省金额、碳排或效率百分比。

## P0：100 分钟必须优先完成

### 1. 共享输入与确认

- 单页双场景切换，默认「今晚吃什么」。支持 JPEG / PNG / WebP、单图与手动录入；原图限制 5MB，传输规则见 MODEL_CONTRACT。
- 识别只生成候选清单。名称、数量、单位可编辑、添加、删除；按用户 2026-09-12 修订，食材与食品耗材自动填入大致用量，标注估算并允许一次确认生成，无需逐项称重；不从图片确认食品安全、可靠材质或尺寸。
- 生成方案前用户点击确认。资源数量为正数，单位用 g / ml / piece；中文显示个、根、块等，内部统一。
- 食材场景提供人数、目标时间、需避开的食材、是否只用现有资源；默认 2 人、目标 30 分钟、只用已有资源。目标是约束，不是成功保证。
- 油盐水、炉头和锅具须显式确认，折叠式「基础用品」减少页面负担；不默认真实拥有，也不要求从照片识别。
- 旧物场景提供用途偏好、目标时间、可用工具；涉及尺寸、稳定性等缺失条件时补充，不从照片假定。
- 上传处说明：图片会发送给 Google Gemini 进行识别；不在本地历史中保存照片。

### 2. 今晚吃什么

- 通常输出一份主食加两道菜。只有材料、人数与时间支持时才给完整菜单；否则说明缺什么或如何缩小目标，不硬凑三道。
- 每道菜包含名称、份数、资源引用与用量、分步做法；整餐有制作顺序、可并行部分、预计用时与必要条件。
- 汇总所有菜的资源占用，服务端计算余量；不能每道菜重复使用同一批鸡蛋、米或油盐，不把模型返回的余量直接充当事实。
- 已确认的忌口不得出现在使用材料、额外补料或替代材料中。明确过敏要求时提醒核对实际食品标签和交叉接触，不承诺模型保证安全。
- 样例的 160g 生米与 30 分钟只属于固定案例约定，不是通用营养标准，也未经过实际烹饪验证。

### 3. 物品第二人生

- 输出两种有区别、步骤简短的方案，一次选择一种；资源只支持一个合理用途时，可如实只给一个并说明原因。
- 每方案包含用途、物品用量、工具、步骤、估时、成品检查。只计算选定方案的占用，两套备选不相加。
- 演示用无盖鞋盒、整块棉布与空罐，提供「玄关随手收纳台」与「桌面小物拍照台」。不要求生成改造后的图片。
- 限定简单桌面、非食品用途；不涉及玻璃切割、电器改造，也不将未确认适用的旧容器用于盛食物。

### 4. 巧用替代与执行

- 提供「只用已有的」约束。关闭后最多列出两类额外消耗品，清楚区分已有与需补充，并说明补充前无法执行的条件。
- 对额外材料点击「这项没有，换个办法」，将其加入排除列表，使用已确认清单重新生成；成功后整体替换方案，重新计算用量。
- 替代须说明调整了哪一步和结果差异；不能只换标签、不改做法，也不能把替代说明再扣一遍材料。
- 没有额外材料时展示当前方案如何利用已有资源，例如清炒版不依赖蚝油、免粘合收纳，不人为制造补料来展示按钮。
- 做法以可勾选步骤呈现，支持复制文字方案与真实反馈。输入改变清除步骤进度，旧结果标记待更新。

### 5. 来源、状态与恢复

- 区分图片候选、用户确认、Gemini 实际结果、固定演示样例；加载样例时图片、输入、结果一起切换并标记来源。
- 固定样例只适用于固定清单，修改后不能继续复用旧样例。任意上传图片不能绑定固定识别清单。
- 更换图片、场景、数量或约束更新输入版本，使旧结果失效；慢请求只有版本匹配才显示，处理时禁止重复提交。
- 无法识别、缺信息、无法成案、超时、密钥/配额错误和非法结构均有可恢复反馈，保留输入，可重试或明确加载样例。
- 真实请求失败不得静默切换为假成功。无 key 时首页仍可打开，显示尚未配置提示，手动输入与固定演示可用。

## P1 与不做事项

P1 仅在 P0 验证后且时间充足时做：本机收藏文字方案、轻微过渡动画。没有收藏功能就不显示「我的收藏」入口；参考效果图不构成额外功能要求。

不做：注册登录、云数据库、社区、二手交易、地图、购物接口、营养评分、碳排计算、支付、复杂拖拽、3D、视频、运行时生图、原生手机应用。第三主题仅作为共享替代机制。

## 技术决定

- 默认 Next.js 16 App Router + TypeScript + Tailwind CSS 4 + npm；图标 lucide-react，验证 Zod。
- 一个应用内两条 Route Handler：`/api/recognize` 与 `/api/plan`。Google 官方 `@google/genai`，默认 `gemini-3.8-flash`；按实际安装版本锁定 SDK。
- 服务端读取 `GEMINI_API_KEY`、`GEMINI_MODEL`。使用 Interactions API，具体以 MODEL_CONTRACT 为准，不混入另一套 API 的参数。
- 不新增 Express、数据库、账号体系或模型 MCP。固定演示本地加载，可选收藏只保存文字，不保存图片或密钥。
- 文档、图片、数据已备好，应用尚未创建；TRAE 初始化时保留现有资料与 Git 历史。
