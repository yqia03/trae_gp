# “就地取材”演示与验收

本文件是准备材料，业务实现、运行和修复由 TRAE 完成。产品主线是“先用家里已有的，少买一点”，面向独居、合租年轻人；今晚吃什么为主场景，物品第二人生为次场景，巧用替代贯穿两者。

以下路演和验收尚未在成品中运行。开发窗口按 100 分钟安排，茶歇不计开发时间；官方路演时长与提交要求公布后再调整。

## 演示资产与来源

- 固定数据：`assets/demo/scenarios.json`。
- 食材图片：`assets/demo/ingredients-input.png`，主代理已在生成后目视核对 2 个番茄、2 个鸡蛋、1 根西葫芦、4 个白蘑菇、1 小碗生米。
- 物件图片：`assets/demo/objects-input.png`，主代理已在生成后目视核对 1 个空无盖罐、1 个空无盖鞋盒、1 块布，呈现玻璃罐及米色棉布外观。
- 两张配图均为 AI 生成图，并非真实拍摄照片。上述检查仅核对可见物件与数量，不是实际识别接口输出，也不能确认克数、尺寸、材质或物品状态。
- 固定数据是人工编排样例，克数、尺寸及“已确认”状态为预置。真实使用须用户核对，不能宣称图片证明了新鲜度或可食用性。

160g 生米、两人份和 30 分钟是本次固定样例的约定，不是全局分量门槛、营养标准或所有菜单的时间上限。真实模式应按用户确认的需求重新规划；不能硬编码“两人必须有 160g 米”，也不能要求所有有效方案都在 30 分钟内完成。

## 90 秒路演脚本

| 时间 | 画面与动作 | 讲述重点 |
|---|---|---|
| 0–12 秒 | 首页展示主张，打开食材场景 | “合租时，家里明明还有东西，我们却经常不知道怎么用。就地取材把现有资源变成今天能做的行动。” |
| 12–27 秒 | 加载食材图，进入可编辑确认清单 | “照片先帮助整理候选项，数量、克数和基础用品由用户确认。今天演示两人、30 分钟。” |
| 27–48 秒 | 展示一份主食、两道菜和并行步骤 | “这里给出完整菜单：白米饭、番茄炒蛋、清炒西葫芦蘑菇。每份材料只分配一次，做法和时间安排放在一起。” |
| 48–60 秒 | 展开巧用替代与资源用量 | “没有蚝油，就用已有盐做清炒版，明确风味变化；不偷偷加上家里没有的材料。” |
| 60–78 秒 | 切到物件图，选择收纳台，再展示另一备选 | “同样的思路用于旧物：鞋盒、布和玻璃罐能成为收纳台。也能改选拍照台；两个方案二选一，切换后重新计算材料。” |
| 78–90 秒 | 回到可执行结果与来源标记 | “我们把现有资源、约束、替代方法和制作步骤连起来，让一个生活点子可以马上动手。” |

使用固定样例时，在 12–27 秒明确说“这里加载预置演示样例”；只有真实请求成功且通过校验时，才说“这是本次真实生成结果”。不要宣称节省了多少钱或多少碳排，也不要把 30 分钟估时说成实测保证。

## 正常流程验收

1. 打开页面：主要入口可见，能区分今晚吃什么与物品第二人生，默认优先展示晚餐场景。
2. 加载固定食材样例：图片和数据均有来源标记，确认页显示 300g 番茄、2 个鸡蛋、200g 西葫芦、80g 蘑菇、160g 生白米。
3. 单独检查油、盐、水、带盖锅、炒锅和双灶的预置确认信息；真实输入时这些项目需用户确认，不能因未出现在照片中就默认存在。
4. 查看菜单：两人份、1 份主食和 2 道菜完整，材料、步骤、估时和前置条件都能找到。
5. 查看资源账本：番茄 300g、鸡蛋 2 个、西葫芦 200g、蘑菇 80g、生米 160g 各自仅分配一次；油共 18ml，盐共 2g，烹饪水 240ml。
6. 查看替代说明：清炒版不依赖蚝油；已计入菜谱的盐不会再扣一遍。未确认的葱姜蒜、糖等不悄悄加入步骤。
7. 检查步骤与时间表：米饭和炒菜并行，30 分钟带估时及条件说明；不支持条件时不能硬套原时间表。
8. 加载固定物件样例：进入人工确认，展示两个互斥备选和制作步骤。收纳台占用 1 罐、1 盒、1 布；拍照台占用 1 盒、1 布，玻璃罐保留。
9. 在两个旧物方案间切换：只保留当前方案的占用，不能将同一块布、同一个盒重复用于两个“已选”项目。
10. 返回输入并修改材料：旧结果明确失效或待更新，不能继续展示旧账本为当前有效结果。

以上通过后记录实际浏览器、时间、输入模式和结果；代码检查或阅读 JSON 不能替代运行验收。

## 错误与断网验收

| 操作或条件 | 必须看到的行为 |
|---|---|
| 上传无法识别或不相关的图片 | 保留图片，允许手动输入或更换图片；不把固定清单伪装成识别结果。 |
| 真实识别给出错误候选 | 用户可以删除、改名、改数量；以用户确认版本为后续方案依据。 |
| 将生米改为 40g，仍要求原样例分配 | 旧结果待更新，解释无法沿用当前约定的 160g 主食分配，提供调整人数、分量或确认其他主食的选择；不把 160g 视为所有两人餐的最低要求。 |
| 双灶改成单灶，或米饭需要更长时间 | 重新评估时间，说明原并行条件不成立；不能承诺仍为 30 分钟。 |
| 油盐、锅具或必要材料未确认 | 提醒补充关键确认，或给出明确不依赖该项的新方案；不能硬凑完整结果。 |
| 模型把未确认材料当成已有、已有用量超额，或补料超出允许范围 | 拒绝作为可执行方案展示；关闭“只用已有的”时，允许最多两类明确标为“需补充”的消耗品，不将其算入已有库存。 |
| 真实模型返回非法结构、空结果或错误 | 正常显示失败；没有空白页面、无休止加载或半份成功结果。 |
| 请求期间断网、超时或接口报错 | 结束等待并保留输入；可重试，或由用户明确点击切换固定样例。 |
| 断网后加载固定样例 | 本地图片与 JSON 可用，来源标记仍明确；不显示真实 API 成功。 |
| 更换输入、场景或连续点击生成 | 旧请求结果不能覆盖新输入；界面清楚说明正在处理哪个输入。 |

资源不充足时，提示应说明“缺什么、影响哪个目标、可以改什么”，不要只显示“生成失败”，也不要自动将未拥有资源加进已拥有清单。

动态替代使用 `scenarios.json` 的 `replanning_acceptance_fixture` 单独验收：载入明确标记的测试夹具，初始胶粘收纳款需额外胶水 5ml；点击“这项没有，换个办法”，检查胶水进入排除项、旧结果失效。返回免粘合方案时，步骤必须改为已有三物的平铺与稳定摆放，补料和用量同步更新；也允许明确返回 `cannot_plan` 并说明原因，不能继续呈现旧胶粘方案为成功。夹具可重复验证界面与校验逻辑，不能替代真实 API 验证，也不要求真实模型返回固定措辞。常规演示仍使用本来就不需胶水的方案，不为展示按钮制造缺项。

## 固定样例与真实模式

- 固定样例用于可重复演示与断网备用；页面明确展示“固定演示样例”，不假装真实识别或生成。
- 真实模式以本次用户确认的资源与约束规划；允许补料时，额外消耗品单列“需补充”，不得冒充已有。请求成功还需检查结构和分配，并标明补充前不能执行的条件。
- 真实请求失败不自动切换来源。用户选择“加载固定样例”后，同步显示样例图片、输入与结果，避免与原上传图片混用。
- 用户修改固定样例后，如系统没有重新规划能力，应提示“输入已变更，请重新生成或恢复样例”，不能继续复用不匹配的结果。
- 图片、JSON 与必要静态资源须能本地读取。是否允许离线样例参赛、是否必须展示真实 AI 调用，以现场规则为准；备用样例不能冒充该项已达标。

## 风险与降级优先级

1. **先保住晚餐闭环。** 图片 → 人工确认 → 菜单与步骤 → 用量核对必须可走通，再做次场景。
2. **先删装饰与扩展。** 复杂动画、历史记录、账户、分享、营养评分、购物链接、节省金额和碳排计算均不挤占核心时间。
3. **识别不稳时保留手动确认。** 手动录入应能继续规划，准确展示来源；真实生成是否可用单独判断。
4. **物件场景来不及时缩短路径。** 保留两套固定备选、步骤、互斥选择和来源标识，取消额外变体；向用户说明实际覆盖范围。
5. **真实服务不稳时明确降级。** 保留错误反馈、输入和重试，使用显式固定样例维持演示；若赛规强制真实调用，记录尚未满足，优先修复。
6. **任何降级都保留用量一致。** 不允许负数剩余、重复分配、照片臆测克数、两套互斥旧物方案同时占用资源。

厨房步骤须以实际食材状态、米种说明和熟度为准；旧物限定稳定桌面上的非食品用途，不做玻璃切割、电器改造，也不把鞋盒等非食品容器用于盛食物。

## 最后 10 分钟

- 用实际演示设备完整走一遍晚餐及物件路径，确认无关键遮挡、失效按钮或输入丢失。
- 检查当前页面的真实 / 固定来源标记，以及计时、人数和数量的可见性。
- 检查本地资产可打开；若要求部署或提交链接，用实际目标地址复测。
- 预演一次请求失败与切换样例，知道从哪个按钮恢复，不临场编造成功解释。
- 记录最终版本、运行入口、已通过项和未验证项，按现场规则提交。
